# آزمون تبدیل امانی به خرید

## دامنه تأییدشده

تبدیل کامل/قسمی در مخزن مشخص تأسیسات خود شرکت، با قیمت توافقی واقعی USD و MT. قرارداد خرید مستقل canonical ساخته می‌شود؛ خروج امانی پیش از ورود ملکی در همان تراکنش است. Ledger/Journal/COGS از مسیر `SimplePurchaseWorkflowService` و Adapter موجود می‌آیند؛ تهاتر امانی با بدهی فروشنده ساخته نمی‌شود.

مالک فروشنده مستقیم استفاده می‌شود. مالک مشتری/شریک فقط پس از تأیید مدیر و مرجع معتبر پیوند با **نقش فروشنده موجود همان شخص** قابل استفاده است. تطبیق براساس نام انجام نمی‌شود؛ هیچ Customer/Supplier/Partner تازه ساخته نمی‌شود. اگر نقش فروشنده آن شخص وجود ندارد، این حالت فعلاً مسدود است؛ این پیوند محدود، مدل هویت مشترک کل سیستم را کامل نمی‌کند.

لغو، خرید/قیمت تمام‌شده/بدهی و خروج امانی را اتمیک برمی‌گرداند. وابستگی پرداخت، دوره بسته، مقدار مسدود، کمبود موجودی ملکی یا خط زمانی منفی مانع ثبت‌اند. لغو مستقل از قرارداد، رسید یا حرکت موجودیِ تبدیل بسته است. لغو خرید دارای ژورنال هنگام خاموش‌بودن حسابداری نیز بسته است؛ خرید تاریخی فاقد ژورنال هنگام روشن‌شدن باید ابتدا از مسیر مصوب خرید تطبیق شود.

Migration افزایشی: `20261011213514_AddCustodyPurchaseConversions`؛ فقط جدول پیوند نقش‌ها و جدول ارتباط تبدیل به قرارداد موجود. هیچ موجودی یا قیمت قبلی backfill نمی‌شود.

## backend و دیتابیس

تست `CustodyConversionPostgresTests` از fixture واقعی PostgreSQL و Adapterهای فعال خرید استفاده می‌کند. 12 سناریو شامل کامل/قسمی، مقدار فزیکی 100، ارزش موجودی، بدهی، لغو و ژورنال معکوس، مصرف ملکی، مسدودی، همزمانی، توکن تکراری، مشتری/شریک، دوره بسته و حساب GL غیرفعال است.

اجرای هدفمند این مرحله: 109 Passed / 0 Failed / 0 Skipped (شامل تست‌های خرید/امانی/لغو و حفاظت حذف). اجرای اول 108 موفق و یک شکست داشت: گارد قرارداد خروج ملکیِ بدون قرارداد را نمی‌شمرد؛ اصلاح با بررسی کل موجودی ملکی زیر قفل مخزن انجام شد و تست بدون تضعیف موفق شد.

دیتابیس آزمایشی خالی تا Migration جدید موفق ساخته شد. ارتقای دیتابیس بازیابی‌شده از بکاپ ساختگی قبلی موفق؛ ورودی ملکی `75.2500` MT با مرجع `SYNTHETIC-PRE-CUSTODY-STOCK` بدون تغییر ماند. EF Pending-model موفق بود.

## مرورگر قابل تکرار

اسکریپت `scripts/qa/custody-conversion-browser.cjs` به Node/Playwright، Chromium و Docker PostgreSQL محلی نیاز دارد. فقط URL localhost و دیتابیس با پیشوند `ptg_oil_accounting_test_` را می‌پذیرد؛ روی Production اجرا نشود.

داده پیش‌نیاز **کاملاً ساختگی**: یک شرکت فعال مالک سیستم، محصول MT، ترمینال خود شرکت، مخزن ظرفیت 100 MT و یک فروشنده فعال؛ شناسه محصول/مخزن/ترمینال/فروشنده برای این fixture همگی `100001`. مخزن باید خالی باشد، یا `PTG_CUSTODY_E2E_RESUME_LOT` به همان بار آزمایشی با مانده 100 MT اشاره کند. حالت Resume رسید تازه نمی‌سازد.

برنامه محلی با Migration خودکار خاموش (`PTG_AUTO_MIGRATE=false`، `Database:AutoMigrate=false`)، ورود خودکار Development خاموش (`PTG_DEV_AUTO_SIGNIN=false`) و اعتبارنامه تستِ صریح bootstrap اجرا شد. نسخه مرورگر این سناریو با GL خاموش است؛ اثبات ژورنال/قیمت تمام‌شده در تست backend با GL فعال انجام می‌شود.

متغیرهای اجرا:

- `PTG_CUSTODY_E2E_USERNAME` و `PTG_CUSTODY_E2E_PASSWORD`: اعتبارنامه همان محیط ساختگی؛ در فایل Git ننویسید.
- `PTG_CUSTODY_E2E_URL`: پیش‌فرض `http://127.0.0.1:5086`.
- `PTG_CUSTODY_E2E_DATABASE`: پیش‌فرض `ptg_oil_accounting_test_custody_browser_resume`.
- `PTG_CUSTODY_E2E_CONTAINER`: پیش‌فرض `mashal-custody-postgres`.
- `PTG_CUSTODY_E2E_CHROMIUM`: پیش‌فرض `/usr/bin/chromium`.
- `PTG_CUSTODY_E2E_OUTPUT`: پیش‌فرض `/tmp`؛ خروجی و screenshotها Commit نشوند.

فرمان: `node scripts/qa/custody-conversion-browser.cjs`.

نتیجه واقعی: ورود با کوکی، رسید 100 MT، تبدیل 40 MT در قیمت 500 USD/MT، PostgreSQL امانی60/ملکی40، لغو با دلیل و PostgreSQL امانی100/ملکی0. در عرض‌های 1440، 390 و 768 پیکسل، عرض صفحه و سند برابر بودند. screenshot موبایل نیز بررسی شد. نخستین اجرای اسکریپت پس از پاسخ POST زودتر از پایان navigation بررسی می‌کرد؛ انتظار جداشدن فرم لغو اضافه شد و اجرای اصلاح‌شده موفق بود. این اصلاح انتظار مرورگر است، نه تضعیف شرط تجارتی.

این سناریو آمادگی E2E قابلیت‌های هنوز پیاده‌نشده کل ماژول را اثبات نمی‌کند.
